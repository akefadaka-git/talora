# TALORA A2 External Format Compatibility Research Memo

- **Document ID:** TALORA-A2-EXT-002
- **Version:** 1.0.0
- **Date:** 19 November 2026
- **Status:** Desk-research evidence; not legal advice and not implementation approval
- **Scope:** Initial import/export formats for TALORA
- **Repository baseline:** `docs/a1-product-definition` as carried on `docs/a1-import-export-referral-entitlements`

## 1. Executive findings

The initial compatibility strategy should prioritize open/documented interchange formats and treat proprietary native formats as separate adapters requiring format-version, licensing and fidelity review.

Key evidence:
- Fountain is a plain-text screenplay markup language, not a WYSIWYG document container. Its own FAQ warns that plain-text interchange can lose styles, dual dialogue and centered text if the target workflow only imports generic text. Pagination is generated by the writing application at render time rather than reliably carried as fixed pages.
- Final Draft's official support article says it does not directly import `.fountain` files; a Fountain workflow may need conversion to FDX or TXT, and the result may require reformatting. This is a concrete reason not to equate file extension acceptance with semantic compatibility.
- DOCX is based on Office Open XML / ISO/IEC 29500, but Microsoft publishes implementation-specific documentation and extensions. TALORA must test against real-world documents and define a supported subset.
- Microsoft describes TXT as losing formatting and RTF as a rich-text interchange format. TXT should therefore be treated as text-level interchange, not a lossless project format.
- PDF is designed to preserve visual layout, not necessarily the semantic screenplay structure required for editing. PDF import must be classified as text/layout reconstruction with user review.

## 2. Format-by-format A2 recommendation

| Format | Recommended initial position | Expected loss/fidelity | Required work |
|---|---|---|---|
| `.talora` | Native full-project package; import/export required | Lossless for supported schema versions | Specify manifest, schema, assets, revision and migration rules |
| PDF | Export P0; import P1 reconstruction | Export: deterministic visual output; import: L3 reconstruction | Text extraction, layout analysis, OCR only where needed, human review |
| TXT | Import/export P0 | Text-only; formatting and semantic metadata may be lost | UTF-8, encoding detection, line-ending policy and screenplay heuristics |
| Fountain | Import/export P1 | Strong screenplay semantics for supported syntax; some advanced production/revision data absent | Parser/writer, syntax-version fixtures, explicit unsupported-construct warnings |
| DOCX | Import/export P1 | L1/L2 depending on document styles, tables, embedded objects and custom features | OOXML subset, style mapping, embedded-font and Ethiopic regression tests |
| RTF | Export P1; import after validation | Rich text, but screenplay semantics are not guaranteed | Define RTF profile and safe parser constraints |
| Final Draft FDX | Import/export P1, subject to compatibility and legal review | L1/L2 per FDX version and supported constructs | Obtain authorized fixtures; schema/version mapping; interoperability tests in target applications |

| Fade In / Celtx native files | No unconditional support promise | L4 until official route is validated | Verify vendor-documented export route, format terms and representative fixtures |

## 3. Evidence and design implications

### 3.1 Fountain

Fountain describes itself as a plain-text markup language for screenwriting. It is portable and useful for screenplay structure, but its own FAQ distinguishes it from richer application document models and notes that plain text may lose text styles, dual dialogue and centered text when imported through generic TXT workflows. It also explains that pagination is typically performed by the application during preview/rendering.

Design implications:
- Treat Fountain as a screenplay interchange format, not TALORA's canonical project format.
- Preserve Fountain-specific syntax and metadata where possible.
- Provide a conversion report for constructs that cannot be represented.
- Do not promise fixed pagination round-trips.

Sources:
- https://fountain.io/
- https://fountain.io/faq/

### 3.2 Final Draft FDX and Fountain interoperability

Final Draft's official support knowledge base states that Final Draft does not directly open/import `.fountain` or `.spmd` files. It advises using FDX or TXT interchange and notes that reformatting may be required. This confirms that application compatibility depends on the target application's actual import behavior, not merely on a format being open or parseable.

Design implications:
- Test TALORA-generated FDX in supported Final Draft versions where authorized test access is available.
- Test imports in Final Draft using genuine FDX fixtures and TXT/Fountain conversion paths.
- Avoid claiming that Fountain output will open natively in every screenplay application.
- Document the exact FDX version/profile supported by TALORA.

Source:
- https://kb.finaldraft.com/hc/en-us/articles/15575076862228-Can-Final-Draft-import-a-file-written-in-a-Fountain-based-screenwriting-program

### 3.3 DOCX / Office Open XML

Microsoft documents Office Open XML as a standard-based format and publishes implementation notes for Office behavior and extensions. This is a suitable basis for DOCX interoperability, but implementation-specific features and third-party application differences require an explicit supported subset.

Design implications:
- Use a standards-compliant DOCX library with reviewed dependency license.
- Do not support macro-enabled DOCM as an import/export target in the initial release.
- Disable external relationships and active content during import.
- Define style mappings for screenplay/stage-play elements.
- Verify Ethiopic glyphs, fonts, page breaks and mixed-script content.

Sources:
- https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/
- https://learn.microsoft.com/en-us/openspecs/office_standards/ms-docx/b839fe1f-e1ca-4fa6-8c26-5954d0abbccd
- https://learn.microsoft.com/en-us/office/compatibility/office-file-format-reference

### 3.4 RTF and TXT

Microsoft's file-format reference describes RTF as carrying document formatting and TXT as plain text where formatting is lost.

Design implications:
- RTF is a useful document interchange target but should not be assumed to preserve all screenplay-specific structures.
- TXT must be clearly labelled as text-only.
- UTF-8 must be the default encoding for TALORA output.
- Import must handle encoding uncertainty without destructive rewriting.

Source:
- https://learn.microsoft.com/en-us/office/compatibility/office-file-format-reference

### 3.5 PDF

PDF should be treated primarily as a fixed-layout output. Importing PDF into an editable script requires reconstruction of logical structures such as scene headings, character cues, dialogue, parentheticals and transitions. Columns, page headers, page numbers, scanned pages and font encoding can make reconstruction uncertain.

Design implications:
- PDF export is P0.
- PDF import is P1 and must show a reviewable reconstruction result.
- Scanned PDFs may require OCR; OCR confidence and language coverage must be disclosed.
- Never claim lossless PDF-to-script conversion.

## 4. Proposed release support tiers

### Initial P0
- `.talora` import/export.
- PDF export.
- TXT import/export.
- User-data export and project archive validation.

### Initial P1
- Fountain import/export.
- DOCX import/export.
- RTF export, then import after parser/security validation.
- Final Draft FDX import/export after authorized fixture and compatibility verification.
- PDF import with reconstruction and review.

### Later P2 / research
- HTML interchange.
- Additional screenplay application formats.
- Fade In and Celtx native/project formats only when official, lawful and testable interchange routes are confirmed.

## 5. Legal and licensing boundary

This memo does not determine the licensing status of any specific parser, writer library, proprietary file format or sample fixture. Before A3:
- Inventory candidate libraries and their exact versions and licenses.
- Review transitive dependencies and distribution obligations.
- Use only lawfully obtained test fixtures.
- Prefer documented official interchange routes for proprietary products.
- Do not use trademarks in a way that implies endorsement or certification.
- Obtain qualified legal review where terms or reverse-engineering restrictions are unclear.

## 6. Research limitations

This is a focused desk review of public documentation, not a complete format conformance study. No parser libraries were installed, no third-party applications were executed, no sample scripts were round-tripped, and no legal opinion was obtained. Therefore, all compatibility claims remain proposed until tested.

## 7. A2 recommendation

Adopt the release support tiers above as the planning baseline, subject to Owner confirmation of the P0/P1 scope. Keep `.talora` as the only full-fidelity native project archive. Treat PDF import as reconstruction, Fountain as screenplay-oriented text interchange, DOCX/RTF as general document interchange, and FDX as a versioned compatibility adapter.
